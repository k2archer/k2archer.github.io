TL;DR

本地 LLM 的流式生成有两个坑，根因是同一个：你跨过了一次语言边界。

  1. 取消失效：llm->response() 在 C++ 里阻塞跑完，Kotlin 侧的协程 cancel() 根本碰不到那个循环。用户说「停」，得等整段说完。
  2. 中文乱码：ostream 回调的 chunk 边界是缓冲区边界，不是字符边界。一个汉字 3 字节，很容易被切在两个 chunk 之间。

我的解法是两个改动：

  • 把生成循环的控制权拿回自己手里：response(..., max_new_tokens=0) 只做 prefill，然后自己用 generate(1) 一个 token 一步地推进——循环在我的 C++ 帧里，每步都能检查停止标志。
  • 加一层 UTF-8 流处理器：攒字节、只吐完整字符、剩下半个留在 buffer 里。

最省事的一点：取消信号不用额外机制——它搭在「送出一个 token」这个已有动作的返回值上。

1. 问题：为什么这俩坑总是一起出现

在一个语音助手（或任何要「说到一半能打断」的交互）里，本地 LLM 的要求比「能跑起来」苛刻得多：

要求 为什么
流式 等整段生成完再播报 = 首字延迟十几秒，交互直接不可用
可取消 用户随时会说「停」/「不用了」，至少要做到下一句话就停
中文正确 中文是 3 字节 UTF-8，而流式输出的切分点是字节级的

前两个和第三个看起来是两类问题，但它们的根因是同一个：

你在 JNI 边界上搬运的是一个「字节流」，而宿主侧需要的是「字符流 + 可取消的执行单元」。

而 JNI 两侧的世界观在这里是不对齐的：

  • 宿主的协程取消是协作式的——它只能打断「主动检查取消状态」的地方。
  • C++ 里那个 response() 是黑盒阻塞调用，它不检查任何东西。

所以 flow.cancel() 对 native 调用完全无效。这是接本地 LLM 时最容易踩的第一个坑，而且它不报错——你会以为取消生效了，因为它不再往你这里送 token 了；但实际上 C++ 还在满负荷跑，用户下一次提问时才发现同一个模型实例卡着。

3. 为什么它不行

坑一：取消完全没有生效

一次回答 100+ token，在手机 CPU 上要跑十几秒。用户说「停」，实际要等十几秒。

我试过三种「看起来应该行」的办法：

尝试 为什么不行
在宿主侧 flow.cancel() 协作式取消，打不到 C++ 的阻塞循环
把 max_new_tokens 调小 那只是上限，不能中途打断；调小了回答就说不完
在另一个线程调 llm->reset() response() 正持有内部状态，并发调用是未定义行为

根本问题：一次 response() 从头到尾占着那个线程，中间没有任何「我可以让出」的时刻。

坑二：中文被切成半个字

ostream 的 xsputn 回调给的是 (const char* s, size_t n)——一个字节缓冲区，n 由 C++ 侧的 flush 时机决定，跟字符边界毫无关系。

所以「你好」这三个字节一对的字符，可能被切成：

你如果在宿主侧对每个 chunk 直接 String(bytes, UTF_8)：

  • chunk 1 → �（替换字符）
  • chunk 2 → �好

用户看到的就是满屏问号，或者更糟——TTS 把 � 念出来。

而且这个问题在英文上完全不会出现（ASCII 是单字节），所以你在英文 prompt 下测试时一切正常，上线到中文才发现。

4. 方案一：把生成循环的控制权拿回自己手里

关键洞察：response() 的 max_new_tokens 参数传 0，它就只做 prefill、不生成。

这一步之后，循环的控制权回到了我的函数帧里。每一轮 generate(1) 之后我都能检查一次 stop_requested。

这就是全部秘诀，但它改变了三件事：

一次 response() generate(1) 步进
取消粒度 整段（不可取消） 一个 token
能否中途换采样参数 不能 能（每步之间）
能否加 token 预算 只能靠 max_new_tokens 上限 能（gen_count < 512）

三个退出条件各有分工：

  • stop_requested —— 用户取消 或 命中 EOS
  • llm->stoped() —— MNN 内部状态机说结束了（双保险：万一文本层 EOS 检测漏了）
  • gen_count < 512 —— 硬预算，防止模型不吐 EOS 时无限生成

这三条同时存在不是冗余，是三个不同的失败模式：取消 / 正常结束 / 异常不收敛。

5. 取消是怎么「搭车」实现的（我认为最巧的一处）

把控制权拿回来之后，还需要一个东西：宿主侧的取消意图，怎么传到 C++ 的循环里？

常见做法是 JNI 里存一个 std::atomic<bool>，再加一个 nativeCancel() 方法。能 work，但要额外一个接口、额外一次跨语言调用、还要处理它和主循环的可见性。

  3. 天然幂等。取消一百次和取消一次效果一样——因为它是「读一个已经关闭的 channel 的状态」，不是「发一封信」。

代价也要说清楚：取消粒度 = 一个 token 的解码时间。 因为检查点在 generate(1) 之后。在 0.5B 小模型的 CPU 推理下这大概是几十毫秒量级——对「停」这个交互足够，但它不是「立即」。

这套取舍在别的引擎里也成立（见 §10 的横向对比）：token 之间的取消是通用下限，想更细就得引入「计算中轮询」的额外回调。

6. 方案二：UTF-8 流式处理器

这个问题的正确解法不是「在宿主侧拼字节」（那样你得在两处都处理残留），而是在字节出口处就保证只吐完整字符。

6.1 先认识一个字符占几个字节

看首字节的高位就知道「这个字符一共几个字节」。这是 UTF-8 设计上最方便的一点——给一个字节就能判断字符边界，不用往回看。

6.2 攒字节，只吐完整的

这段的核心是那个 break 的语义：

i + length > size 时不是「丢弃这个残缺字符」，而是「不消费它」。

utf8Buffer 会一直保留这半个字符，等下一个 chunk 的字节到了接上、凑成完整的，再一起吐出去。

这个区别很关键。如果你「不完整的就丢掉」，那每个汉字被切断的位置都会永久丢失字节——乱码会累积。而「留着不消费」，最终所有字节都会被消费恰好一次。

细节：streambuf 还有单字节路径 overflow()（sputc 走这里）。示例里 MNN 的写入都走 xsputn，所以我没重写它；但如果你的引擎会逐字符 <<，记得把 overflow() 也桥一遍，否则会丢单字符。

7. EOS 与「流怎么结束」

流式生成最容易出的边角问题不是生成，是收尾。我这里有三种结束方式，处理得不一样：

结束方式 C++ 侧 宿主侧
文本命中 EOS 检测到 eos_str → 不写入 response、保存历史、stop_requested = true 收到 token == null → close()
llm->stoped() 触发 循环退出，但文本 EOS 没走到 兜底：循环结束后补发一次 onProgress(null)
用户取消 stop_requested = true Flow 已关闭，不需要再通知

EOS 检测依赖 MNN 的一个约定：命中 EOS 或 max_tokens 时，它会把 eos_str 作为独立 chunk 写进 ostream：

这个做法能 work，但它有两个前提，都值得写死在注释里：

  1. eos_str 不会出现在正常的生成内容里。 用 <eop>、<|endoftext|> 这类 token 是安全的；如果你把 eos_str 配成 "。" 这种正文里会出现的字符，就会在第一个句号处截断。这是个很容易配错、又很难查的坑。
  2. EOS 一定作为独立 chunk 到来。 上面的 find 是对「这一批完整字符」做子串匹配；如果引擎把 EOS 和正文混在同一个 batch 里吐出来，这批正文会被整批丢掉。用「独立 chunk」是 MNN 的保证，换成别的引擎时这条要重新验证。

7.1 这里有个我自己写反了的坑（重点）

那个「兜底补发 onProgress(null)」是必须的：没有它，宿主的 callbackFlow 就永远不会 close()，awaitClose 永远不会被调用——Flow 挂在那里不收尾，上层等一个永不到来的完成信号。

但我在复盘时发现，兜底的判据很容易写反。我最初写的是：

推演两条路径就会发现问题：

  • 文本 EOS 命中：回调里已经发过一次 null；fallback 不 push → size == before 为真 → 又发一次 null（重复，但因为 close() 幂等所以无害）。
  • stoped() 触发、文本 EOS 没命中：fallback 会 push assistant → size == before 为假 → 不发 null → Flow 永不 close()。

也就是说：这段兜底恰好漏在了它本该兜底的那条路径上。 正确写法应该让判据直接跟着「是否已结束」走，而不是绕一圈用 history.size() 去推断：

stop 为 true 只有两种情况：EOS（已发过 null）或用户取消（Flow 已关）——两种都不需要再发。stop 为 false 说明是 stoped() / 预算退出，这时才补发。一个布尔量就够了，不要用 history 的长度去间接推断状态。

教训：收尾逻辑一旦用「副作用（push）之后的间接状态」当判据，就极易写反，而且症状是「挂住」而不是「报错」，最难查。判据要直接指向「是否已经结束」。

8. 怎么证明「取消真的取消了」

这一点值得单独说，因为它是本机 LLM 最容易自欺欺人的地方：取消之后 token 确实不再到达宿主了，但那可能是因为上游不转发，而 C++ 还在满负荷跑。

我的验证思路是三条独立的证据，缺一不可：

证据 怎么拿
① C++ 循环真的退出了 循环退出后打日志 generation finished: %d tokens, stop=%d, stopped=%d——stop=1 且 gen_count 明显小于 512，说明是主动停而不是跑完
② 宿主侧 Flow 真的关了 callbackFlow 的 awaitClose { log("Flow closed") } 必须被调用
③ 取消后还能继续用 再发一次 submit() 能正常流式输出。如果 C++ 没退出，下一次调用会卡在 mutex 上或返回垃圾

第 ③ 条最容易被忽略但最重要。「取消了」的正确含义不是「不再有输出」，是「实例回到了可再次使用的状态」。

8.1 怎么量化「取消时延」

「取消粒度 = 一个 token」这句话，最好是给数而不是给形容词。可以这样测：

  1. 打开 MNN context 自带的计时（见附录），拿到 decode_us（单步解码耗时）；
  2. 在「发出取消」到「循环退出」之间打两个时间戳，差值即取消时延；
  3. 重复 20 次取 P50 / P95。

预期结论是：取消时延 ≈ 一个 decode_us 的量级。如果测出来远大于它，那大概率是取消信号没有真的搭上车（比如 trySend 的返回值没被回传，或 C++ 没读那个返回值）。

9. 这个实现目前的五个缺口

我不想只讲「我做成了什么」。这套骨架有五个明确的问题，都还没修——真正的工程是「知道它哪里会塌」：

9.1 阻塞调用没有切线程

callbackFlow 里如果没有 flowOn(Dispatchers.IO) / withContext(IO)，这几十秒的阻塞就跑在收集者的 dispatcher 上——上游天真地在 Main 上 collect，就是主线程阻塞几十秒。

目前没炸是因为调用方恰好都在后台线程。这是个靠「用的时候小心」维持的正确性，应该修但还没修。（最小骨架里已经帮你加上 withContext(IO)。）

9.2 Executor 硬编码 CPU + 1 线程，配置项是空的

所以配置对象的 backendType 传了也一定不生效——代码自己声明了不读它，你设成 "opencl" 只会得到一个仍在 CPU 上跑的实例。

threadNum 则需要实测才能确定：它会经 llm->set_config() 传给 MNN，但 Executor 在 set_config 之前就已经用 1 线程创建好了。到底以哪个为准，取决于 MNN 内部是否会用 config 重建 Executor——这一点我没有验证，所以不能断言它生效。

对 0.5B 小模型来说单线程能跑；如果将来要上更大的模型，这里是第一个要查的瓶颈。麻烦的是它不会报错，只是慢——这类「配置静默失效」是最难查的一类问题。

9.3 停止标志是文件级静态变量

原因和限制：

这些是模块级全局变量（.so 加载后唯一）。MNN Llm 接口要求 ostream 回调中设置停止标志，无法通过 Llm 实例传参。当前单例会话保证单会话，无并发风险。若未来需要多实例，需改为以 nativePtr 为 key 的 map。

换句话说：这套实现只能有一个模型实例。 想同时加载两个模型（比如小模型做快问快答、大模型做复杂任务），需要重构这一层。

9.4 整个 .cpp 文件 0 处 env->ExceptionCheck()

JNI 层最容易致命的错误是 Java 侧抛了异常、C++ 没检查继续往下走。这个文件里：

  • GetMethodID 的结果从不校验——如果回调方法名被 R8 改名 / 混淆，方法 ID 变成 nullptr，下一行 CallBooleanMethod(nullptr, ...) 直接 SIGSEGV；
  • GetStringUTFChars 的返回值从不判空——OOM 时会构造 std::string(nullptr)，是 UB。

这两条是 JNI 代码的必修课。 如果你的回调方法名会变（混淆、反射、动态代理），第一个坑几乎必然踩到。

10. 横向对比：别的引擎怎么做「取消」

「token 间取消」是通用下限，「计算中取消」是普遍加分项。本文的「回调返回值搭车」只是其中一种取舍：

引擎 取消机制 特点
MNN（本文） JNI 回调返回值搭车 零额外接口、无原子变量；粒度 = 1 token
llama.cpp llama_set_abort_callback(ctx, cb, data)，计算过程中被周期性轮询，返回 true 即中止 能中断「还在处理超长 prompt」的阶段，粒度细于 token 间；需额外的回调注册
ONNX Runtime Ort::RunOptions::SetTerminate() 可从另一个线程调用，终止使用该 RunOptions 的 Run；需把 RunOptions 一路传下去
llama.cpp 的 token callback 每个 token 后回调 与本文粒度相同：只能停在 token 之间，停不进一次长 prompt 的计算里

有意思的是：llama.cpp 官方也承认「token 回调只能停在 token 之间，停不进长 prompt 的计算里」——这和本文「取消粒度 = 1 token」的取舍是同一个下限。要突破它，就得像 abort_callback / SetTerminate 那样引入「另一个线程能看到的终止标志 + 计算内轮询」。本文选搭车，是因为语音助手里 1 token 的粒度已经够用，且能省掉一整套跨线程可见性。

11. 一句话总结

本地 LLM 的流式 + 取消 + 中文，看起来是三个功能，实际上是一件事：

在跨语言边界上，你要保证搬运的东西是「对端的语义单位」——对 C++ 是控制点，对宿主是完整字符。

具体到两行代码：

  • response(..., max_new_tokens=0) 把生成循环拿回来 → 于是有了控制点
  • i + length > size → break（而不是丢弃）→ 于是有了字符边界

剩下的都是在这两个基础上补时序：EOS 兜底、退出条件、取消后可用。
