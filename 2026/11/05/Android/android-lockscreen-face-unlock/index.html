手机在桌上黑着屏。人走过来，前置相机认出他，屏幕亮，锁屏上出现一句问候，然后进桌面。

听起来像一次人脸识别。难的是后面四段：怎么让相机在锁屏后继续跑，怎么让卡片出现在锁屏之上，怎么把屏幕点亮，怎么解除锁屏。每一段归不同的系统服务管，每一段都能单独失败。

我在一台 Android 14 机器上把这条链路走通了，也被国产 ROM 打回三次。下面的日志、时间戳和常量都来自真机。设备是 iQOO Neo7 SE，Funtouch 14.1，targetSdk 34，识别栈是 Camera2 加 MLKit 加 TFLite。

先看全景

一条链路五段。

常驻识别。前台服务加 Camera2。锁屏后相机会被停，事件流断流。

在场判定。应用自己做去抖。做不好，咳嗽一声就被问候，或者永远不触发。

锁屏可见。NotificationManager 的全屏 Intent。失败时只有一条通知，屏幕上什么都没有。

点亮屏幕。PowerManager 和 WindowManager。失败时卡片在黑屏里渲染，用户看不见。

解除锁屏。KeyguardManager。失败时卡片在，但还在锁屏后，进不了桌面。

让相机在锁屏时也跑

锁屏后普通后台进程会被冻结，相机句柄会被回收。唯一稳定的做法是带 camera 类型的前台服务。

Android 14 对 camera 类型的 FGS 加了一条很多人踩的规则：不能裸调 startForeground，必须在 eligible state 里启动，通常是 App 在前台，或者由可见操作触发。在 Service.onCreate() 里直接调，在系统拉起或后台场景会抛 SecurityException 当场崩溃。所以要把前台化抽成可重入的守卫，在 onStartCommand 和“注册人脸”这类必然来自可见界面的入口里调：

识别栈不需要预览。Camera2 + ImageReader(YUV_420_888) 就能拿到原始帧，不创建 TextureView/SurfaceView，界面上什么都不出现。这是“常驻但无感”的前提。

两个容易忽略的成本细节。

MLKit 的 landmark、contour、classification 全关掉。业务只读 boundingBox，轮廓点云却会显著抬高单帧耗时和临时对象分配。

CameraCharacteristics 只取一次并缓存。传感器方向、镜头朝向、帧率档一辈子不变，但每帧 getCameraCharacteristics() 等于一次 binder 调用外加约 17.8KB 的 metadata 分配与拷贝。常开服务连续跑几小时，这类调用会把进程的映射条目堆到内核上限。

常开相机最贵的不是推理，是帧本身。Camera2 每出一帧都会为 result metadata 分配约 16KB 原生缓冲，由 GC 延迟回收；30fps 常开时这是进程“映射条目”持续增长的主要来源之一。

所以采集压到设备支持的最低固定帧率档（目标 10fps），处理侧再按 intervalMs = 300 节流，实际约 3Hz。代价是：你没有“出现”和“离开”事件，只有连续观测。这正是下一段要解决的事。

3Hz 的流里没有“出现”

事件流长这样：每 300ms 一帧，Hit 是认出了某人，Miss 是有脸但没匹配上，NoFace 是这帧没脸。没有出现，没有离开，没有多人。语义全得自己做。

朴素的“看到脸就问候”在真机上坏得很惨：转头的瞬间、路过镜头的一帧、甚至一次误识别，都会触发全屏打扰。我的做法是一张很薄的时序状态机。

同一 faceKey 连续至少 3 帧，首末跨度至少 900ms，才算到场。这挡的是单帧误识别，大约等于“站定一秒”。

置信度 1 - distance 要过门槛，挡的是“陌生人被认成最近邻”。

连续无人脸或他脸 5s，才算离开。这挡的是转头、遮挡、低头。

离开 10 分钟以上，才算“回来”。短时走开不重复问候。

冷启动时，第一张确认的脸只建基线。不然一开机就问候主人。

3s 内出现两个以上不同 faceKey，按多人处理，给中性文案或者跳过。

它是个纯 Kotlin 类，不碰 Android API，所以能在 JVM 上直接跑时间序列单测：

喂一串带时间戳的观测，断言只在第 N 帧后产出 Arrived。这比真机复现便宜两个数量级。

置信度门槛只能现场标定。最初设计写的是 1 - distance ≥ 0.75，翻译过来是 L2 距离 ≤ 0.25。但本机引擎实测同一个人的距离在 0.77 到 1.43 之间波动。按 0.75 的门槛，问候永远不会触发。

问题在于这个引擎没有匹配阈值：库里只要有人，它就返回最近的那个，哪怕来的是陌生人。所以距离门槛是挡住陌生人的唯一信号，且强依赖模型与光照，只能现场标定。最终默认值定成 minConfidence = -0.5（距离 ≤1.5，比实测最大值 1.427 留一点余量），并且不做 0 到 1 截断。一旦把 1.4 和 2.0 都压成 0，门槛就失去意义。

阈值类参数，方案里写的是先验，真机能跑通的是后验。部署前必须用真实陌生人样本复核。

去抖只回答“有人来了”。要不要现在亮屏是另一层，用固定顺序短路，顺序本身就是产品语义。

功能关闭，Drop(DISABLED)。

静默时段，默认 22:30 到 07:30，Drop(QUIET_HOURS)。

人脸没绑定任何用户，Drop(NO_IDENTITY)。

多人且未开启多人问候，Drop(MULTI_PRESENCE)。

距该用户上次问候不到冷却时间，Drop(COOLDOWN_USER)。

最近 1 小时问候次数达上限，Drop(RATE_LIMIT)。

去重键命中，Drop(DUPLICATE)。

当前环境没有可用通道，Drop(NO_CHANNEL)。

其余走 Show(route)。

一个反直觉但重要的取舍：decide() 返回 Show 的瞬间就记账，冷却、频率、去重全落账，哪怕随后展示失败也不重试。

因为 OEM 拦截往往不是偶发的。如果失败就回滚记账，人脸流每 300ms 一帧，会立刻形成“决策、失败、回滚、再决策”的重试风暴。宁可一次失败，等下一轮到场。

锁屏可见只有一条标准路

锁屏上放东西，Android 给了好几条路，能同时满足“点亮屏幕、覆盖锁屏、后台可用”的只有一条。

手段 点亮屏幕 覆盖锁屏 后台可用 结论
直接 startActivity 靠 turnScreenOn 可以 不行：Android 10+ 后台启动限制 仅前台场景补充
唤醒锁 + 已有 Activity 可以 需临时 showWhenLocked 可以 兜底
全屏 Intent → Activity 系统点亮 showWhenLocked 系统代发，不受 BAL 限制 主路径
高优先级通知（heads-up） 通常不点屏 只是通知条 可以 不采用
SYSTEM_ALERT_WINDOW 悬浮窗 需配合唤醒锁 因 ROM 而异 可（豁免 BAL） 兜底、最终形态

全屏 Intent 是系统替你把 Activity 放到锁屏之上并点亮屏幕，这正是闹钟和来电的机制。其他做法都在跟后台启动限制（BAL）和 OEM 自启动管理搏斗。

taskAffinity 要独立。与主界面共用任务栈时，解锁转场（keyguardGoingAway）会把主界面顶回前台，问候页被 pause 然后 destroy，表现是“卡片闪一下”。

不要加 noHistory。熄屏拉起时 Activity 会被系统以 sleep 暂停，noHistory 立刻销毁它。同样的“闪一下”，但原因完全不同。这两个坑我是分开踩的，排查耗了一整晚。

主题要透明且禁用预览窗口，否则锁屏上会先闪一个白底：

全屏 Intent 必须挂在一条 notification 上，载体不合格，全屏也不会触发。

channel 必须 IMPORTANCE_HIGH，低重要级不会触发全屏 Intent。

setFullScreenIntent(pi, highPriority = true) 的布尔参数是“高优先级”，不是“仅锁屏时全屏”。锁屏时系统直接拉起 Activity，亮屏时系统自行决定退化成 heads-up。这个行为由系统控制，应用管不了。

PendingIntent 只加 FLAG_ACTIVITY_NEW_TASK。加 CLEAR_TOP 在独立任务栈下会制造“创建即结束、重启”竞态，实测纯负收益。

Android 14 改了权限模型。Android 12 和 13 上，USE_FULL_SCREEN_INTENT 安装即授予。Android 14 起，只有以通话或闹钟为核心功能的应用默认获得。其他应用 canUseFullScreenIntent() 返回 false，全屏 Intent 降级成 heads-up，不点亮屏幕。用户可手动开启：Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT，带 package: Uri。部分 ROM 裁剪了该页，要回落到应用详情页。

但这个 API 不可信。真机上它返回 true，系统投递时照样拒绝。所以它只能当提示，不能当路由依据。

亮屏不是加个 flag

点亮屏幕有两条路径。

一条是 Activity 自点亮，setTurnScreenOn(true)。由全屏 Intent 或 SAW 直启拉起时，系统侧点亮。

一条是主动点亮，SCREEN_BRIGHT_WAKE_LOCK or ACQUIRE_CAUSES_WAKEUP。需要自己控制时机，比如先点亮再投递。

第二条是关键细节：ACQUIRE_CAUSES_WAKEUP 才是让屏幕亮起来的部分，SCREEN_BRIGHT_WAKE_LOCK 只保证亮着的时候别暗。务必 setReferenceCounted(false)，即使某条异常路径漏了 release()，超时后系统也会自动收回。

那个“卡片闪 40ms”的坑，是我在这件事上花时间最多的地方。现象是：锁屏下识别到人，屏幕亮了，卡片出现，然后几十毫秒内消失，设备停在锁屏上。

第一版以为是 onStop 里的 finish()，删掉，没用。

第二版以为是 noHistory，删掉，49ms 变成 68ms，还是没用。

第三版以为是任务栈，加独立 taskAffinity，53ms，依然没用。

真正的原因在事件日志里：

Activity 记录刚创建，ROM 就以 app-request 的理由主动结束了它。客户端稍后跑的 onCreate/onResume 是一个已经被判死刑的实例。

但在这之前还有个更基础的问题被它掩盖了：熄屏状态下投递。系统会在 Activity 创建后立刻用 sleep 暂停它（wm_pause_activity ... sleep），此时任何“stop 即销毁”的配置都会让卡片秒没。

所以修复的第一步不是改生命周期，而是先点亮屏幕，等系统真的进入交互状态，再投递：

三个数字都是真机调的。显示电源上电通常不到 500ms，所以 800ms 足够；再等 250ms 让窗口系统稳定。

唤醒锁的释放交给定时器。如果唤醒锁跟着 Activity 的 onDestroy 释放，而 Activity 恰好被 ROM 提前杀掉，屏幕就会在卡片淡出过程中黑掉。所以“谁申请、谁定时释放”，与 Activity 生命周期解耦：申请时带“卡片时长加 1s”的余量，用协程定时释放。

亮屏是不可逆的。普通应用没有 DEVICE_POWER 权限，无法主动熄屏。能做的只有：只申请有限期唤醒锁；卡片结束时移除 FLAG_KEEP_SCREEN_ON；接受“屏幕会亮到系统息屏超时”这个现实。

这点在需求评审时就该讲明白，否则产品会以为你能“亮 3.5 秒然后自己黑掉”。

解锁的语义

requestDismissKeyguard 是唯一“正规”的解锁入口，但有三个容易漏的前提。

必须在 Activity 里调用，且该 Activity 已 setShowWhenLocked(true)。

它不会绕过安全锁屏。设备有 PIN 或密码时，它会弹出系统凭据界面，盖住卡片。

它是异步的，结果走 KeyguardDismissCallback 的三个回调。第三条意味着“调用了”不等于“解锁了”，必须等回调。

按设备形态分叉。

无屏幕锁，也就是滑动锁，自动解除，直接进桌面。

有屏幕锁，不请求解除，只覆盖显示。卡片盖在锁屏上，仍需用户自行验证。

请求失败或取消，补试 1 次，仍失败则记录。卡片结束，回到锁屏。

“补试 1 次”是刻意的。解锁转场期间系统会短暂切换前台，第一次请求有概率被取消；但无限重试会变成“每 300ms 弹一次凭据界面”。

不要用的东西：disableKeyguard()（API 13 起废弃，对安全锁无效）、FLAG_DISMISS_KEYGUARD（同上）、DevicePolicyManager（只有设备所有者或管理员可用）、任何“模拟输入密码”的路子（商店政策与用户信任都不允许）。

边界要写进文档：普通应用能自动解开的，只有本来就没锁的设备。这句说清楚，后面所有预期都对得齐。

可观测性不是多打点日志，而是事件契约。七类事件，单行 JSON：

posted 只表示通知已入队，不代表任何可见性。visible 才是成功信号，带 via 与延迟。delivery_failed 带 stage、reason、elapsedMs，能直接定位哪一级挂了。人脸标签脱敏，首字加 ***，设备上不落图像。

没解决的部分

写技术文章容易只写成功路径。这件事真正值得记的是失败，以及为什么它还没解。

现象：visible 之后 49 到 68ms 卡片消失，事件日志显示 wm_create_activity 后 4ms 就是 wm_finish_activity reason=app-request，紧接着 wm_focused_root_task ... finish-top、wm_task_removed。客户端的 onCreate/onResume 甚至在记录销毁之后才跑（TransactionExecutor: Skip pre-destroyed transaction）。所以“上报可见”是成功的，卡片也确实渲染了，只是几十毫秒后就被抹掉。

已排除的假设：noHistory 导致 stop 即销毁，已移除，无效；onStop 主动 finish()，已移除，无效；与主界面共用任务栈，改独立 taskAffinity，无效；FLAG_ACTIVITY_CLEAR_TOP 竞态，去掉，无效；熄屏 sleep 暂停，先亮屏已生效（pause 消失），仍被 finish。

也就是说，这不是应用侧的配置问题，而是 ROM 的“顶层任务不可聚焦就 finish-top”策略。vivo 系还有独立的“后台弹出界面、应用启动管理”开关，很可能是同一拦截器的另一面。

如果 Activity 通道就是救不回来，架构上要退一步：展示交给 SYSTEM_ALERT_WINDOW 系统级浮层，不受 Activity 生命周期影响，权限已授予；Activity 只做透明解锁，它唯一不可替代的能力就是 requestDismissKeyguard。

代价是两部分要分别做可见性回报，收益是“卡片停留时长”终于可控。

拆分之前我加了一个兜底：载体通知延迟 800ms 再取消，且 onDestroy 时移除该回调。卡片被提前销毁时，通知会留到 10s 超时，用户至少还能在通知栏看到那句问候。原则是：当一条通道不可靠时，别把体验全押在它身上。

前置相机只有一颗

还有一件和代码无关、但一定会撞上的事：前置相机只有一颗。

系统的“人脸解锁”需要在前置相机上跑。你的常驻识别服务长期占用同一颗相机（dumpsys media.camera 里本进程一直是 active client）。结果是系统 facelock 拿不到相机，lockscreen.options=enable_facelock 开着也解不了锁。

这不是 bug，是硬件资源冲突。可选的路只有三条。

自己做识别加自己做解锁，让出相机给系统，改用系统回调，但有锁设备仍需验证。

把相机让给系统，放弃常驻识别，只在亮屏时识别。

分时复用，亮屏、锁屏切换时主动释放相机，复杂，切换有几百毫秒延迟。

结论：别两边都要。要么你是“识别的主人”，要么你是“系统解锁的旁观者”。硬要并存，用户看到的就是“它有时候认得出我，有时候认不出”。

三种档位

第一次做，建议直接从“中等”开始，但一定要把闭环一起做。没有闭环，你在真机上根本分不清“没生效”和“生效了但你没看见”。

最小档：通知加全屏 Intent 加 showWhenLocked。能做到锁屏出现卡片、点亮屏幕。做不到自动解锁。

中等档：上面加 requestDismissKeyguard，仅 secure=false。无锁设备直接进桌面。有锁设备仍需验证。

完整档：上面加可见回调闭环、降级阶梯、自定义识别。各 ROM 尽量可用、可诊断。仍受 ROM 的 Activity 策略影响。

最后

人脸识别解决的是“知道是谁”。“看一眼就进桌面”真正难的是权限、时序和确认。

锁屏可见只能靠全屏 Intent，它由系统代发，绕过后台启动限制。

点亮屏幕要先于投递，否则 Activity 会被 sleep 抢在创建之前。

解锁只在“本来就没锁”的设备上成立，有锁就必须让用户自己验证。

而所有这一切的前提，是你能证明它真的发生了。notify() 成功不算，Activity 创建不算，只有“用户看得见”的那一帧才算。

几个常量：采集处理间隔 300ms（约 3Hz）；相机目标帧率 10fps；到场确认 3 帧、跨度至少 900ms；离开确认 5s；重新到场 10min；置信度门槛 1 - distance ≥ -0.5，本机同类 L2 距离 0.77 到 1.43；可见 ack 超时 2000ms，全屏 Intent 冷启动实测约 1.3s；等待 isInteractive 最多 800ms，轮询 50ms；亮屏后稳定等待 250ms；卡片时长 3500ms，产品定义，可 2.5 到 5 秒；载体通知超时 10s，取消延迟 800ms。
