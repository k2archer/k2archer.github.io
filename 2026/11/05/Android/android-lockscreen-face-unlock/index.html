TL;DR

给一个常驻 App 加上「锁屏时认出人 → 点亮屏幕 → 解锁」，难点不在识别，而在后面那几段：

  1. 识别人脸和在锁屏上出现是两套完全不同的权限模型。锁屏可见只有一条标准路径：全屏 Intent 拉起一个带 showWhenLocked + turnScreenOn 的 Activity——这就是来电和闹钟的做法。
  2. 点亮屏幕和解除锁屏是两件事，且都必须发生在「已经显示在锁屏之上」的那个 Activity 里。熄屏状态下直接投递，Activity 会被系统以 sleep 暂停，配合 android:noHistory 直接销毁，用户只看到卡片闪 40ms。
  3. notify() 不抛异常，不代表用户看见了。 第一次真机测试里，应用日志写着「已展示」，而 Activity 从头到尾没被创建过——系统在 appops 层把全屏 Intent 拒了。修复方向不是继续写解锁代码，而是给投递加闭环。
  4. 最后，这台 ROM 会在 Activity 创建后 约 4ms 主动 finish 它（reason=app-request），独立任务栈也规避不了。成熟形态是：展示交给系统级浮层，Activity 只负责解锁。

1. 全景：五段链路，五套系统服务

「看一眼就进桌面」不是一次 API 调用，是五段串联，每段归不同的系统服务管：

# 阶段 谁负责 失败时的表现
1 常驻识别 前台服务（camera 类型）+ Camera2 锁屏后相机被停，事件流断流
2 在场判定 应用自己（去抖） 咳嗽一声就被问候，或永远不触发
3 锁屏可见 NotificationManager（全屏 Intent） 只有一条通知，屏幕上什么都没有
4 点亮屏幕 PowerManager / WindowManager 卡片在黑屏里渲染，用户看不见
5 解除锁屏 KeyguardManager 卡片在，但还在锁屏后，进不了桌面

2. 第一段：让相机在锁屏时也在跑

2.1 前台服务三件套

锁屏后普通后台进程会被冻结、相机句柄会被回收，唯一稳定的做法是带 camera 类型的前台服务：

Android 14 对 camera 类型的 FGS 加了一条很多人踩的规则：**不能裸调 startForeground**，必须在「eligible state」里启动——通常是 App 在前台，或由可见操作触发。在 Service.onCreate() 里直接调，在系统拉起或后台场景会抛 SecurityException 当场崩溃。所以要把前台化抽成可重入的守卫，在 onStartCommand 与「注册人脸」这类必然来自可见界面的入口里调：

2.2 识别栈：检测、特征、最近邻

相机不需要预览。Camera2 + ImageReader(YUV_420_888) 就能拿到原始帧，不创建 TextureView/SurfaceView，界面上什么都不出现——这是「常驻但无感」的前提。

两个容易忽略的成本细节：

  • MLKit 的 landmark / contour / classification 全关掉。 业务只读 boundingBox，轮廓点云却会显著抬高单帧耗时和临时对象分配。
  • CameraCharacteristics 只取一次并缓存。 传感器方向、镜头朝向、帧率档一辈子不变，但每帧 getCameraCharacteristics() 等于一次 binder 调用外加约 17.8KB 的 metadata 分配与拷贝。常开服务连续跑几小时，这类调用会把进程的映射条目堆到内核上限。

2.3 成本：3Hz 是省出来的

常开相机最贵的不是推理，是帧本身。Camera2 每出一帧都会为 result metadata 分配约 16KB 原生缓冲，由 GC 延迟回收；30fps 常开时这是进程「映射条目」持续增长的主要来源之一。

所以采集压到设备支持的最低固定帧率档（目标 10fps），处理侧再按 intervalMs = 300 节流，实际约 3Hz。代价是：你没有「出现」和「离开」事件，只有连续观测。这正是下一段要解决的事。

3. 第二段：3Hz 的连续流，没有「出现」这回事

事件流长这样：每 300ms 一帧，Hit（认出了某人）、Miss（有脸但没匹配上）、NoFace（这帧没脸）。没有出现、没有离开、没有多人。语义全得自己做。

3.1 去抖规则

朴素的「看到脸就问候」在真机上坏得很惨：转头的瞬间、路过镜头的一帧、甚至一次误识别，都会触发全屏打扰。我的做法是一张很薄的时序状态机：

到场确认 同一 faceKey 连续 ≥3 帧，首末跨度 ≥900ms 抗单帧误识别，≈「站定一秒」
置信度门槛 1 - distance ≥ 阈值 挡「陌生人被认成最近邻」
离开确认 连续无人脸/他脸 ≥5s 抗转头、遮挡、低头

3.2 置信度门槛只能现场标定

最初设计写的是「置信度 1 - distance ≥ 0.75」，翻译过来是 L2 距离 ≤ 0.25。但本机引擎实测同一个人的距离在 0.77–1.43 之间波动——按 0.75 的门槛，问候永远不会触发。

问题在于这个引擎没有匹配阈值：库里只要有人，它就返回最近的那个，哪怕来的是陌生人。所以距离门槛是挡住陌生人的唯一信号，且强依赖模型与光照，只能现场标定。最终默认值定成 minConfidence = -0.5（距离 ≤1.5，比实测最大值 1.427 留一点余量），并且不做 0..1 截断——一旦把 1.4 和 2.0 都压成 0，门槛就失去意义。

教训：阈值类参数，方案里写的是先验，真机能跑通的是后验。部署前必须用真实陌生人样本复核。

3.3 该不该打扰：策略短路表

去抖只回答「有人来了」。要不要现在亮屏是另一层，用固定顺序短路，顺序本身就是产品语义：

# 条件 结果
1 功能关闭 Drop(DISABLED)
2 静默时段（默认 22:30–07:30） Drop(QUIET_HOURS)
3 人脸没绑定任何用户 Drop(NO_IDENTITY)
4 多人且未开启多人问候 Drop(MULTI_PRESENCE)
5 距该用户上次问候 < 冷却时间 Drop(COOLDOWN_USER)
6 最近 1 小时问候次数达上限 Drop(RATE_LIMIT)
7 去重键命中 Drop(DUPLICATE)
8 当前环境没有可用通道 Drop(NO_CHANNEL)
— 其余 Show(route)

一个反直觉但重要的取舍：**decide() 返回 Show 的瞬间就记账**（冷却、频率、去重全落账），哪怕随后展示失败也不重试。

因为 OEM 拦截往往不是偶发的：如果失败就回滚记账，人脸流每 300ms 一帧，会立刻形成「决策→失败→回滚→再决策」的重试风暴。宁可一次失败、等下一轮到场。

4. 第三段：锁屏可见——只有一条路是标准做法

4.1 五种手段对比

手段 点亮屏幕 覆盖锁屏 后台可用 结论
直接 startActivity 靠 turnScreenOn 可以 不行：Android 10+ 后台启动限制 仅前台场景补充
唤醒锁 + 已有 Activity 可以 需临时 showWhenLocked 可以 兜底
全屏 Intent → Activity 系统点亮 showWhenLocked 系统代发，不受 BAL 限制 主路径
高优先级通知（heads-up） 通常不点屏 只是通知条 可以 不采用
SYSTEM_ALERT_WINDOW 悬浮窗 需配合唤醒锁 因 ROM 而异 可（豁免 BAL） 兜底 / 最终形态

一句话：全屏 Intent 是系统替你把 Activity 放到锁屏之上并点亮屏幕，这正是闹钟和来电的机制。其他做法都在跟后台启动限制（BAL）和 OEM 自启动管理搏斗。

4.2 Manifest

两个属性是踩坑后加的：

  • taskAffinity 独立：与主界面共用任务栈时，解锁转场（keyguardGoingAway）会把主界面顶回前台，问候页被 pause → destroy，表现是「卡片闪一下」。
  • **不要加 noHistory**：熄屏拉起时 Activity 会被系统以 sleep 暂停，noHistory 立刻销毁它——同样的「闪一下」，但原因完全不同。这两个坑我是分开踩的，排查耗了一整晚。

4.3 通知只是载体，但载体有硬性要求

全屏 Intent 必须挂在一条 notification 上，而载体不合格，全屏也不会触发：

  • channel 必须 IMPORTANCE_HIGH，低重要级不会触发全屏 Intent；
  • setFullScreenIntent(pi, highPriority = true) 的布尔参数是「高优先级」，不是「仅锁屏时全屏」。锁屏时系统直接拉起 Activity，亮屏时系统自行决定退化成 heads-up——这个行为由系统控制，应用管不了；
  • PendingIntent 只加 FLAG_ACTIVITY_NEW_TASK。加 CLEAR_TOP 在独立任务栈下会制造「创建即结束/重启」竞态，实测纯负收益。

4.4 Android 14 改了权限模型

  • Android 12/13：USE_FULL_SCREEN_INTENT 安装即授予；
  • Android 14 起：只有以通话/闹钟为核心功能的应用默认获得。其他应用 canUseFullScreenIntent() 返回 false，全屏 Intent 降级成 heads-up，不点亮屏幕；
  • 用户可手动开启：Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT（带 package: Uri）。部分 ROM 裁剪了该页，要回落到应用详情页。

但这个 API 不可信——见 §7.1，真机上它返回 true，系统投递时照样拒绝。所以它只能当提示，不能当路由依据。

5. 第四段：亮屏——不是加个 flag

5.1 两条点亮路径

路径 实现 适用
Activity 自点亮 setTurnScreenOn(true) 由全屏 Intent / SAW 直启拉起时，系统侧点亮
主动点亮 SCREEN_BRIGHT_WAKE_LOCK or ACQUIRE_CAUSES_WAKEUP 需要自己控制时机（如先点亮再投递）

第二条是关键细节：ACQUIRE_CAUSES_WAKEUP 才是让屏幕亮起来的部分，SCREEN_BRIGHT_WAKE_LOCK 只保证「亮着的时候别暗」。务必 setReferenceCounted(false)——即使某条异常路径漏了 release()，超时后系统也会自动收回。

5.2 那个「卡片闪 40ms」的坑

这是我在这件事上花时间最多的地方。现象：锁屏下识别到人，屏幕亮了，卡片出现，然后 几十毫秒内消失，设备停在锁屏上。

第一版以为是 onStop 里的 finish()，删掉，没用。第二版以为是 noHistory，删掉，49ms → 68ms，还是没用。第三版以为是任务栈，加独立 taskAffinity，53ms，依然没用。

真正的原因在事件日志里：

Activity 记录刚创建，ROM 就以 app-request 的理由主动结束了它，客户端稍后跑的 onCreate/onResume 是一个已经被判死刑的实例。

但在这之前还有个更基础的问题被它掩盖了：熄屏状态下投递。系统会在 Activity 创建后立刻用 sleep 暂停它（wm_pause_activity ... sleep），此时任何「stop 即销毁」的配置都会让卡片秒没。

所以修复的第一步不是改生命周期，而是先点亮屏幕，等系统真的进入交互状态，再投递：

三个数字都是真机调的：显示电源上电通常 <500ms，所以 800ms 足够；再等 250ms 让窗口系统稳定。

5.3 唤醒锁的释放交给定时器

如果唤醒锁跟着 Activity 的 onDestroy 释放，而 Activity 恰好被 ROM 提前杀掉，屏幕就会在卡片淡出过程中黑掉。所以「谁申请、谁定时释放」，与 Activity 生命周期解耦：申请时带 卡片时长 + 1s 的余量，用协程定时释放。

5.4 亮屏是不可逆的

普通应用没有 DEVICE_POWER 权限，无法主动熄屏。能做的只有：只申请有限期唤醒锁；卡片结束时移除 FLAG_KEEP_SCREEN_ON；接受「屏幕会亮到系统息屏超时」这个现实。

这点在需求评审时就该讲明白，否则产品会以为你能「亮 3.5 秒然后自己黑掉」。

6. 第五段：解锁——语义比 API 重要

6.1 requestDismissKeyguard 的三个前置条件

它是唯一「正规」的解锁入口，但有三个容易漏的前提：

  1. 必须在 Activity 里调用，且该 Activity 已 setShowWhenLocked(true)；
  2. 它不会绕过安全锁屏。设备有 PIN/密码时，它会弹出系统凭据界面，盖住卡片；
  3. 它是异步的，结果走 KeyguardDismissCallback 的三个回调。

第三条意味着「调用了」不等于「解锁了」，必须等回调。

6.2 按「有没有屏幕锁」分叉

设备形态 行为 用户看到
无屏幕锁（滑动锁） 自动解除，直接进桌面 卡片 → 桌面
有屏幕锁 不请求解除，只覆盖显示 卡片盖在锁屏上，仍需自行验证
请求失败/取消 补试 1 次，仍失败则记录 卡片结束，回到锁屏

「补试 1 次」是刻意的：解锁转场期间系统会短暂切换前台，第一次请求有概率被取消；但无限重试会变成「每 300ms 弹一次凭据界面」。

6.3 不要用的东西

disableKeyguard()（API 13 起废弃、对安全锁无效）、FLAG_DISMISS_KEYGUARD（同上）、DevicePolicyManager（只有设备所有者/管理员可用）、任何「模拟输入密码」的路子（商店政策与用户信任都不允许）。

边界要写进文档：普通应用能自动解开的，只有「本来就没锁」的设备。 这句说清楚，后面所有预期都对得齐。

7.4 降级阶梯

有了可见性判定，降级才有意义。最终四级，每级只尝试一次，绝不回退：

几个要点：fsiBroken 只缓存在进程内，重启后重探一次（一次偶发失败不该永久废掉主通道）；第 ② 级依赖 Settings.canDrawOverlays()，这里只用来豁免后台启动限制，不渲染常驻悬浮窗；降级前先 cancel() 掉载体通知，否则「通知 + 卡片」双显。

7.5 日志契约

可观测性不是「多打点日志」，而是事件契约。七类事件，单行 JSON：

  • posted 只表示「通知已入队」，不代表任何可见性；
  • visible 才是成功信号，带 via 与延迟；
  • delivery_failed 带 stage / reason / elapsedMs，能直接定位哪一级挂了；
  • 人脸标签脱敏（首字 + ***），设备上不落图像。

这套契约的价值是把「感觉不太灵」变成可查的数字：比如「卡片停留多久」，用 finished - visible 一减就知道，不必猜。

8. 没解决的那部分

写技术文章容易只写成功路径，但这件事真正值得记的是失败，以及为什么它还没解。

现象：visible 之后 49–68ms 卡片消失，事件日志显示 wm_create_activity 后 4ms 就是 wm_finish_activity reason=app-request，紧接着 wm_focused_root_task ... finish-top、wm_task_removed。客户端的 onCreate/onResume 甚至在记录销毁之后才跑（TransactionExecutor: Skip pre-destroyed transaction）。所以「上报可见」是成功的，卡片也确实渲染了——只是几十毫秒后就被抹掉。

已排除的假设：

假设 验证结果
noHistory 导致 stop 即销毁 已移除，无效
onStop 主动 finish() 已移除，无效
与主界面共用任务栈 改独立 taskAffinity，无效
FLAG_ACTIVITY_CLEAR_TOP 竞态 去掉，无效
熄屏 sleep 暂停 先亮屏已生效（pause 消失），仍被 finish

也就是说，这不是应用侧的配置问题，而是 ROM 的「顶层任务不可聚焦就 finish-top」策略。vivo 系还有独立的「后台弹出界面 / 应用启动管理」开关，很可能是同一拦截器的另一面。

如果 Activity 通道就是救不回来，架构上要退一步：

展示交给 SYSTEM_ALERT_WINDOW 系统级浮层（不受 Activity 生命周期影响，权限已授予），
Activity 只做透明解锁（它唯一不可替代的能力就是 requestDismissKeyguard）。

代价是两部分要分别做可见性回报；收益是「卡片停留时长」终于可控。

拆分之前我加了一个兜底：载体通知延迟 800ms 再取消，且 onDestroy 时移除该回调。卡片被提前销毁时，通知会留到 10s 超时，用户至少还能在通知栏看到那句问候。原则是：当一条通道不可靠时，别把体验全押在它身上。

9. 结构性冲突：系统人脸解锁 vs 常开相机

还有一件和代码无关、但一定会撞上的事：前置相机只有一颗。

  • 系统的「人脸解锁」需要在前置相机上跑；
  • 你的常驻识别服务长期占用同一颗相机（dumpsys media.camera 里本进程一直是 active client）；
  • 结果是系统 facelock 拿不到相机，lockscreen.options=enable_facelock 开着也解不了锁。

这不是 bug，是硬件资源冲突。可选的路只有三条：

  1. 自己做识别 + 自己做解锁：让出相机给系统，改用系统回调（但有锁设备仍需验证）；
  2. 把相机让给系统：放弃常驻识别，只在亮屏时识别；
  3. 分时复用：亮屏/锁屏切换时主动释放相机（复杂，切换有几百毫秒延迟）。

结论：别两边都要。 要么你是「识别的主人」，要么你是「系统解锁的旁观者」。硬要并存，用户看到的就是「它有时候认得出我，有时候认不出」。

10. 三种档位，按投入选

档位 做法 能做到 做不到
最小 通知 + 全屏 Intent + showWhenLocked 锁屏出现卡片、点亮屏幕 自动解锁
中等 上面 + requestDismissKeyguard（仅 secure=false） 无锁设备直接进桌面 有锁设备仍需验证
完整 上面 + 可见回调闭环 + 降级阶梯 + 自定义识别 各 ROM 尽量可用、可诊断 仍受 ROM 的 Activity 策略影响

第一次做建议直接从「中等」开始，但一定要把闭环（§7.3）一起做。没有闭环，你在真机上根本分不清「没生效」和「生效了但你没看见」。

11. 验收清单

一次成功链路长这样（无锁设备）：

判断标准不是「看到了卡片」，而是这五条同时成立：

  1. appops 是 allow，不是 default；
  2. visible 在 posted 之后 2000ms 内出现；
  3. keyguard=dismissed，且设备真的进了桌面；
  4. finished - visible ≈ 3500ms（卡片真的停留了）；
  5. wm_finish_activity 的 reason 不是你自己的代码。

第 5 条就是我卡住的地方——前四条全绿，第五条永远指向 app-request。

12. 一句话总结

人脸识别解决的是「知道是谁」，而「看一眼就进桌面」真正难的是权限、时序和确认：

  • 锁屏可见只能靠全屏 Intent，它由系统代发，绕过后台启动限制；
  • 点亮屏幕要先于投递，否则 Activity 会被 sleep 抢在创建之前；
  • 解锁只在「本来就没锁」的设备上成立，有锁就必须让用户自己验证；
  • 而所有这一切的前提，是你能证明它真的发生了——notify() 成功不算，Activity 创建不算，只有「用户看得见」的那一帧才算。
