目标读者：做端侧语音助手 / 实时语音交互的人；尤其是被「打断不太灵」「它总少听我半句话」折磨过的人
环境：Android + Kotlin 协程；流式 ASR（会持续吐 partial）；输入侧有 USB 麦克风阵列（硬件 AEC）与手机麦克风两种路径
代码：正文片段是删节后的骨架，保留能说明设计的最少结构，不依赖某个具体 SDK；数字与日志来自真机

TL;DR

免提场景下打断 TTS 有两个互相冲突的要求：要快（几百毫秒内让位）和不能误判（VAD 假阳性会掐掉正常播报）。多数实现只能二选一。

我的做法是把「发现疑似人声」和「确认打断」拆成两个阶段：

  1. VAD 只负责发现疑似有人说话 → 压低音量（不停播报）+ 起一个探测 ASR 轮；
  2. 直到拿到首个非空 ASR partial 才真正打断；
  3. 确认后把探测轮晋升为正式轮，而不是停掉重开——用户的第一句话一个字都不会被解码两次。

代价是多了一个 500ms 量级的 pre-roll 缓冲和一个 2.5s 的探测超时；收益是打断不再依赖 VAD 的准确率。

1. 问题：一个「等一下」

先对齐一下术语：打断（barge-in）指的是用户在助手播报（TTS）时开口，系统立刻让位、停止播报，并直接开始听用户接下来说的那句话。

播报进行到第 3 秒，用户说「等一下」。

你的目标：~100ms 内停止播报，并立刻开始听用户接下来要说什么。

这件事有三个隐藏难点，只有真做过才会依次撞上：

难点 现象
回声自打断 手机免提时 TTS 自己的声音进麦克风 → VAD 判「有人说话」 → 无限打断自己
假阳性 40ms 的关门声/咳嗽就能骗过 VAD → 正常播报被莫名掐断
首音节丢失 确认打断后重启 ASR，此时 ring buffer 已被清 → 用户「等一下」的「等」字没了

第三条最不容易被发现，因为用户体验上它只是「它总是少听我半句话」，很难归因。

3. 为什么它不行

3.1 坑一：为了修回声，我把打断功能整个删掉了

grep 串 次数

12 次打断意图，11 次被这行守卫丢弃——打断功能在结构上等于不存在。而我当时以为「打断已经做了，只是不太灵」。

这是个值得单独说的教训：「功能写了」和「功能可达」是两件事。 一个永远走不到的分支，在代码评审里看起来和正常分支一模一样。

3.2 坑二：假阳性会掐掉正常播报

去掉守卫之后，噪声开始骗过 VAD。THINKING（已在准备答案、还没开口）阶段被误取消，用户会觉得「它突然不说话了」。

单点 VAD 信号在这个问题上是不可靠的输入——而打断是一个不可逆操作（TTS 停了就得从头说）。

3.3 坑三：首音节被吃了

即使前两个坑都绕过，「确认打断 → 停 TTS → 重新 startListening」这个流程还有个隐藏时序问题：

ASR 是流式的，用户说「等一下」的时候，「等」这个字已经过去了几百毫秒。如果你在确认打断之后才 startListening()，前面那几百毫秒的音频已经在 ring buffer 里被冲掉了。

4. 方案：把「疑似」和「确认」拆开

核心想法很简单：VAD 不该有权力直接打断，它只该有权力「请求确认」。

整条链路的状态转移如下（--> 表示定时器兜底，不是正常路径）：

四层，逐层收窄误判：

层 机制 解决哪个坑
L1 置信度分带 高置信直通，低置信丢弃，中间带才走确认 假阳性
L2 duck 先于打断 疑似人声先压低 TTS 音量但不停播报 体验（用户感觉「它要让位了」）+ 给确认争取时间
L3 探测轮（probe turn） 用 ring buffer 的 pre-roll 播种一个探测 ASR，等第一个非空 partial 首音节 + 假阳性
L4 晋升（promote）而非重启 确认后把探测轮原地转为正式轮 首音节被二次解码

4.1 L1：置信度分带

两个细节值得说：

① 冷却期必须覆盖「直通」路径。 我一开始只给中间带加冷却，结果高置信路径会形成乒乓：刚打断完，下一帧 VAD 还是 speechActive，于是再打断一次。注释里写的「否则会形成乒乓」就是踩过之后补的。

② 中间带不再由 VAD 超时自动确认。

我原来的实现是「duck 之后等一个 VAD 确认超时，语音还在就确认打断」。这仍然是纯 VAD 判断，只是加了个延迟——噪声持续 200ms 照样骗过。这一版把它彻底交给 ASR。（代码里那句「不再由 VAD 超时自动确认」就是这个决定的留痕；那个 150ms 的确认常量现在只剩 THINKING 路径在用。）

4.2 L2 + L3：duck 一下，然后起一个探测轮

先说清 duck：它是「把 TTS 音量临时压低，但不停止播报」。用户听感上是「它明显要让位了」，而系统这边还没做任何不可逆的决定。

-1L 这个参数是重点。 正常唤醒路径传的是唤醒词所在帧号，管线会把唤醒词对应的帧过滤掉，只保留唤醒之后的用户语音：

打断时没有唤醒词要裁，所以传 -1L，把 500ms pre-roll（preRollDurationMs = 500）原样喂给 ASR。

这就是「坑三」的答案：探测轮启动时，用户已经说出去的那几百毫秒已经在缓冲里了，不是从零开始听。

补一句术语：ring buffer 是采集侧一直在跑的环形录音缓冲，pre-roll 指「触发那一刻往前回溯的那一段」。它的作用就是让触发之前的音频不丢——这正是打断场景最需要的东西。

4.3 L4：晋升，而不是重启

这是整套设计里我最满意的一处。

关键点：这里没有 stopListeningTurn()，也没有第二次 startListeningTurn()。

探测轮从「为了确认而临时起的轮次」原地变成「正式识别轮」。用户说的「等一下」这条音频流，从头到尾只被解码了一次。

如果按直觉实现（确认 → 停 → 重开），会出现：探测轮已经解出「等一」，你把它停掉，再开一个干净的轮次——用户得把「等一下」重说一遍，或者只有后半句「下」进了新轮次。这是很多语音助手「总是听不全第一句」的真正原因。

5. 三重兜底：真正让它能上设备的部分

一个只在 happy path 上正确的打断实现，会在真机上随机失效。我最后落的是三条超时，各自负责一类失败：

兜底 触发条件 常量
探测超时 起了探测轮但 2.5s 没有任何 partial → 放弃，恢复音量 BARGE_IN_ASR_CONFIRM_TIMEOUT_MS = 2_500L
语音提前结束 VAD 说人声结束了，但还没有 partial → 宽限 600ms 等尾巴词，超时再放弃 BARGE_IN_ASR_GRACE_MS = 600L
晋升后 TTS 未停 已进入 INTERRUPTING，但 TTS 的停止回调没来 → 600ms 后强制推进状态机 PROMOTE_REPLY_STOP_GRACE_MS = 600L

第二条尤其重要，因为它对应一个真实场景：用户说了半句就停下（「那个……」）。这时候 VAD 会立刻报人声结束，但 ASR 可能还差几十毫秒才吐出第一个 partial。如果你一收到 silence 就 abort，会把一个真实的打断当噪声丢掉。

第三条是最「脏」但最必要的一条。状态机里 REPLYING → INTERRUPTING 依赖 TTS 引擎的停止回调；如果引擎因为任何原因没回调，会话就卡在 INTERRUPTING——用户看到的是「它变成哑巴了」。

注意它没有 abort 探测轮——即使被迫强推状态，识别还在继续。这个细节决定了「引擎回调丢了」的后果是「打断稍慢一点」而不是「用户这句话白说了」。

6. 我怎么证明它真的没二次解码

这是我觉得这篇最值得抄的一点。

打断这种东西，靠人工体验测试是测不出来「有没有重复解码」的。所以我把它写成了一条可断言的不变量：

「首音节不丢」不是一个说法，是一条断言。

startListeningTurnCount == 1 + stopListeningTurnCount == 0
= 整段交互只起过一轮 ASR，且中途从未停过它。

这条断言的另一个好处：它锁死了一个设计决策。以后谁想在这里加一次 stop/start，测试会立刻红，并且报错信息直接告诉你为什么不能加。

同一个测试文件里还有一条更细的：空 partial 不算确认。

这对应一个真实的坑：ASR 在噪声段有时会吐出空白 partial。如果按「收到 partial 就打断」实现，用户咳嗽一声就能打断播报。

7. 边界：三个前提，外加一句需要提前说清的话

我之前在别的地方犯过一个错：把「我在自己项目里跑通了」说成「这是通用解法」。这里先把边界讲清楚——它有三个明确的前提和缺口。

7.1 前提一：它依赖「回声已经被处理过」

也就是说，在手机上是「没有打断」，不是「打断得很准」。这是我欠的账，方案已经写好了，还没实现。

这也是为什么前面反复强调「门控」：整套设计的安全性建立在「VAD 说的是人声，不是 TTS 回声」这个前提上。前提不成立时，正确的做法是关掉打断，而不是把阈值调高——调高只是把误判率降到「偶尔很尴尬」。

7.2 前提二：让位只要 2–8 ms，停播要 470 ms——差的那 439 ms 全在等确认

我后来真的测了（2026-11-01，一台 Android 手机 + USB 麦克风阵列）。两个数现在同源了：

指标 实测 目标 判定
barge_in_duck（起音 → 音量压低） 2 / 8 ms ≤ 100 ✅
barge_in_stop（起音 → 播报停止） 467 / 472 ms ≤ 400 ❌ 差 ~70 ms

partial 到手之后，停播只用了 26 ms。

也就是说：

我的动作一点都不慢（8 ms 就让位了）。慢的是「我必须先确认你确实在说话」。

而这正是这个方案的全部代价——它用 439 ms 的确认时间，换了「不被 VAD 假阳性掐掉播报」。

想压到 100 ms 级只有一条路：硬件 VAD 一起来就直接停播（而不是先 duck 再等 partial）。那会把回声风险原样拿回来——TTS 自己的声音被当成人在说话。所以我没做。

这个数我一开始是测不到的，原因值得单独说

第一版埋点里 barge_in_duck 一条都没落盘。原因是两个时钟不同源：

bargeInOnsetMs 记在软件 VAD 上，但 duck 是被硬件 VAD 提前 117 ms 触发的。于是每次 duck 发生时，onset 还是 0，直接 return。

两个不同源的时钟量同一件事，就是坑。 修法是把起音时刻统一到触发 duck 的那一路记录——修完之后 onset=hwdect，两个数终于同一个基线、可以相减了。

顺便，这个缺陷还让旧的 barge_in_stop（315 ms）偏小——因为它从软件 VAD 起算，漏掉了硬件 VAD 抢先的那 117 ms。

这个领域里大家都在说「低延迟」。我拿到的两个真实数字是 8 ms（让位） 和 470 ms（停播），而且我知道后者 94% 是设计代价、不是实现低效。这两个事实都要说清楚，否则第一个数字会被当成第二个来宣传。

7.3 前提三：几个关键常量是经验值

  • 连续打断上限 3 次
  • 打断冷却 2 秒
  • 探测超时 2.5 秒
  • 语音结束宽限 600ms

这四个数没有一个是从测量里来的，是调出来的。它们很可能不是最优值——如果你在做一个类似的东西，请从测量开始，别抄我的常数。

7.4 另外：样本量很小

上面那两个延迟数字目前只有 2 次打断（n=2），是我在调通后顺手抓的两条。它们的量级我认为是可信的（2/8 ms 和 467/472 ms 两次都对得上），但具体数值不宜当基准。如果要拿它做对比，先补到 10 次以上再说话。

这一条我特意留在文里，是因为「n=2 的延迟结论」在技术文章里太常见了，而它其实只能支撑「量级」这一个结论。

8. 一句话总结

打断的难点不在「检测到人声」。真正的难点是两件事：你还得决定信不信它，以及在信它的时候不能丢掉用户已经说出口的那半句话。

把这两件事拆开——VAD 只请求确认，ASR 才给结论，探测轮晋升而不重启——这三步就把一个「总是不太灵」的功能变成了可断言的行为。
