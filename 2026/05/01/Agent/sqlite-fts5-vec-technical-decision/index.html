一、引言：一个真实的选型困境

我参与的一个项目，是一个基于 LangGraph 的多代理自主助手。它有两个绕不开的检索需求：

  1. 长期记忆——把和用户聊过的事实、偏好、决策存下来，之后按语义召回；
  2. 工具/技能检索——几百个工具和技能挂在系统里，用户一句话过来，得在几十毫秒内找到最相关的那几个。

一开始，记忆模块用的是 ChromaDB。这几乎是当时的”标准答案”：你有个向量，你把它存起来，你按相似度查它，完事。问题出在它和这个项目的”其余部分”并不生活在同一个世界里。

项目本身跑在 Windows 单机上，技术栈是 Python + asyncio + SQLite，主数据全在一个 .sqlite 文件里。而 ChromaDB 意味着：多一个独立依赖、多一份向量数据的生命周期管理、和主库之间天然割裂——一份记忆既要写业务表、又要写向量库，两边的一致性还得自己操心。更别提它在某些 Windows 环境下的安装和启动，本身就是一滩事。

项目的 factory.py 里，至今保留着那次迁移的痕迹——原本基于 ChromaDB 的分支逻辑被整段注释掉，只留一行说明：

这行注释，就是我写下这篇文章的起点。

真正让我停下来重新思考的，是这样一个反问：向量检索，真的需要一个”专门的向量数据库”吗？ 如果我的数据量只有几万到几十万条，如果我只跑在一台机器上，如果我还同时需要”关键词精确命中”——那么，一个已经躺在项目里、零额外服务、和业务数据同库同事务的 SQLite，能不能把这件事一起办了？

答案是能。而它的钥匙，是 SQLite 的扩展机制：FTS5 补上全文检索，simple 扩展补上中文分词，sqlite-vec 补上向量检索。这篇文章想讲清楚的，不是”怎么写代码”，而是为什么这个组合在单机轻量场景下是比独立向量库更务实的决策，以及它真实的代价在哪里。

二、决策约束清单：先立标尺，再比方案

技术选型最常犯的错，是先爱上某个技术，再回头给它找理由。正确顺序应该反过来：先写清楚”我的约束是什么”，然后让方案来对号入座。

所以在这一步，我不谈任何具体数据库，只列约束。每一个约束都不是拍脑袋，而是直接来自项目的现实：

# 约束 为什么它成立 它反过来排除了什么
1 单机 Windows 部署 目标用户就是本地跑，没有 K8s、没有运维团队 所有”必须起独立服务”的方案成本陡增
2 中小规模数据 记忆 + 工具 + 技能加起来，量级在万到十万级 分布式 ANN、十亿级召回这些能力用不上
3 关键词 + 语义双检索 用户说”帮我查明天会议”，关键词和语义是互补的，不是二选一 只有向量检索、没有全文检索的方案不够用
4 中文场景 系统交互语言是中文，而中文分词是全文检索的隐藏前提 FTS5 默认 tokenizer 对中文几乎失效
5 与现有栈无缝融合 项目是 asyncio + LangGraph，主数据在 SQLite 引入另一套连接、序列化、事务语义，是负资产
6 低运维、易迁移备份 实验性质项目，快速迭代 备份/迁移要复制整个服务而不是一个文件的方案，都算额外成本

这张表本身就是文章最重要的”标尺”。后面所有方案的对比，都是拿方案去撞这六条约束，而不是拿方案互相 PK 性能。

这里有两处需要提前点破，因为它们决定了整套决策的走向：

第一，中文是条硬约束。 FTS5 自带的 tokenizer（unicode61、ascii 等）是为英文这类空格分词语言设计的，面对”我爱吃苹果”这种无空格文本，分词效果很差，全文检索基本失效。这意味着：如果用 SQLite 的 FTS5，就必须额外加载一个中文分词扩展。项目里用的是 simple（wangfenjin/simple）扩展，编译产物就放在 plugins/libsimple-windows-x64/，在连接初始化时加载：

换句话说，**”SQLite 支持中文全文检索”这件事不是免费的**，它建立在”你能加载这个原生扩展”之上——这也是后面第 6 章要诚实交代的代价之一。

第二，”中小规模”是最容易被忽略的约束。 很多人一谈检索就默认要上分布式、要横向扩展，却忘了先问一句”我的数据到底有多大”。如果你的量级根本到不了专用向量库的舒适区，那么专用向量库带来的不是性能红利，而是纯纯的运维负担。这条约束，是整套决策能够成立的地基。

标尺立好了，接下来就是把候选方案逐个放上去量。那才是真正的对决。

三、备选方案横向对比：把方案放上标尺

结论先说：SQLite 组合的胜出，是”约束贴合度”的胜利，不是”性能最强”的胜利。 换个规模、换个团队，结论可能完全不同。

把上一章的六条约束当成标尺，候选方案逐个量一遍：

方案 部署形态 关键词检索 向量检索 中文友好 与现有栈融合 运维成本
ChromaDB 独立 Python 包 ✗ 需另配 ✓ ✓ 弱（数据分离） 中
Milvus 独立服务（容器） ✗ 需另配 ES ✓ ✓ 弱 高
FAISS 纯库、无服务 ✗ ✓ ✓ 中 中
pgvector 依赖 PostgreSQL ✓ tsvector ✓ 需另配分词 中 中高
SQLite + FTS5 + sqlite-vec 单文件、无服务 ✓ ✓ ✓ simple 扩展 强（同库同事务） 低

逐一看这张表里”被淘汰”的方案，你会发现它们几乎都不是输在”不够强”，而是输在”不匹配”：

  • Milvus / 独立向量服务：性能天花板最高，但代价是”起一个服务 + 维护一个服务”。对一个跑在用户 Windows 单机上、没有运维团队的项目，这是纯负担（约束 #1、#6 直接否决）。
  • FAISS：很好的库，但它只管向量，全文/关键词检索要自己另起一套。而我的场景里关键词命中（比如用户说的确切日期、人名）和语义召回同样重要，缺一个就不完整（约束 #3 否决）。
  • pgvector：其实是 SQLite 组合的”同门师兄”——同样是”在关系库里做向量”。但它要求先有一个 PostgreSQL，这恰好和”项目主数据已经在 SQLite 里”的现实冲突，等于为了检索去换掉整个存储底座（约束 #5 否决）。
  • ChromaDB：就是项目最初的选择，也最接近需求，但它的数据生命周期独立于主库，记忆/工具既要写业务表又要写向量库，一致性要靠自己兜（约束 #5 否决）。

最后看胜出的那行：SQLite + FTS5 + sqlite-vec。它之所以成立，是因为它几乎是为约束 #1、#5、#6 量身定做的——不引入任何新服务，向量和全文索引就住在你已有的那个 .sqlite 文件里，和业务数据同库、同事务。备份迁移是复制一个文件，删除依赖是删一个文件。

但这里必须立刻补一句诚实的话：这张表的成立，完全建立在约束 #2「中小规模」之上。SQLite 的单文件模型注定了它不适合高并发写入和十亿级向量。它不是更强的方案，它是”够用且最省心”的方案。 这句话，请读者务必记住，它是第 6 章代价讨论的前提。

四、为什么这个组合能成立：技术可行性论证

结论先给：SQLite 本身既不懂”全文检索”，也不懂”向量相似度”，但它的扩展机制允许你把这两块能力”装”进去。 装完之后，你得到的是三张表——主表、FTS 表、向量表——住在同一个文件里，用同一套事务。

论证到这儿，结论已经立住：技术上，”SQLite + FTS5 + sqlite-vec”是一个自洽的、单文件的检索栈，它用扩展补齐了能力，用触发器抹平了索引维护的复杂度。下一章，进入真正决定它好不好用的部分——落地实现的关键设计。

五、落地实现的关键设计：一次查询完成混合检索

前面讲的是”为什么能成立”，这一章讲”实际跑起来长什么样”。实现的核心，可以收敛成三个设计决策：融合公式、单 SQL 融合、多级降级。

5.1 融合公式：关键词分数 × 语义分数，加权相加

检索时，系统会同时跑两条路——FTS5 关键词匹配和向量语义匹配——然后把两者的分数加权融合：

其中两个子分数分别这样计算：

  • 语义分数：vec_score = 1 / (1 + distance)。distance 是余弦距离，vec_distance_cosine 直接给出；距离越小，vec_score 越接近 1。
  • 关键词分数：fts_score = -rank / 100。FTS5 的 rank（BM25）是负数且越小越相关，取负后变成”越大越相关”，再除以 100 缩放到可比的量级。

权重 0.7 / 0.3 意味着语义匹配占主导，关键词作为辅助信号。这个比例是调出来的经验值，不是铁律，后面第 6 章会指出它其实有个”量纲不可比”的隐患。

5.2 用一条 SQL 把两条路合起来

最精妙的地方在于：融合不是用 Python 在内存里算的，而是一条 SQL 里用 LEFT JOIN 同时挂上 FTS 和向量两个子查询，数据库直接返回排好序的结果：

几个细节值得展开：

  • **LEFT JOIN 而非 INNER JOIN**：保证”只命中关键词”或”只命中语义”的记录都不会被漏掉，靠 COALESCE 给缺失的那一路填 0。
  • MATCH 放进了 JOIN 的 ON 条件：这样 FTS 的匹配和向量匹配可以并行展开，而不是先硬性过滤。
  • **向量子查询先 ORDER BY distance LIMIT ?**：这是为了限制候选集大小，但这里埋了个坑——先截断再回联，可能丢掉”向量不太像但关键词非常像”的结果。第 6 章会专门说。

六、诚实的代价：这套方案的三个真实软肋

前面一直在说它有多好，现在该说它哪里不好。决策型文章的价值，恰恰在于把代价说透——否则读者照着选型，会在你闭口不谈的地方踩坑。

6.1 扩展加载的跨平台脆弱性

这是最大的软肋。simple 分词器和 sqlite-vec 都是原生扩展，意味着它们和操作系统、CPU 架构、Python 版本强绑定。Windows 上是 .dll，Linux 上是 .so，路径还不一样。项目里干脆写死了一串候选路径逐个尝试：

这种”猜路径”的做法，在固定部署环境下能跑，但换一台机器、换一个平台，就可能静默失败。更糟的是，项目里对加载失败的处理是降级而不是报错——向量加载失败时只是打一条 warning 日志，系统继续用 FTS5 跑。好处是健壮，坏处是你可能根本不知道向量检索已经悄悄失效了。

6.2 融合分数”量纲不可比”

回头看 5.1 的公式：vec_score 落在 (0, 1]，而 fts_score = -rank/100 的量纲完全由 BM25 的分数分布决定，两者直接线性相加，严格来说不是数学上等价的融合，而是一个工程近似。

它的问题在于：当某条记录关键词高度命中时，-rank/100 可能远大于 1，瞬间盖过语义分数，导致”字面匹配但语义一般”的记录排到前面。这个 /100 是拍脑袋定的缩放系数，换一批数据、换一个分词器，最优值就变了。

公平地说，这不算 bug，而是这类轻量融合的通病。真要严谨，应该像项目里 IoT 工具检索那套实现一样——两条路分开查，各自做 min-max 归一化到 [0,1]，再加权合并。但那就不是”一条 SQL 搞定”了，多了一次查询往返。**”一条 SQL”的简洁，和”分数严谨”的正确，在这里是取舍关系。**

6.3 向量预过滤的召回风险

5.2 的 SQL 里，向量子查询先 ORDER BY distance LIMIT ? 再回联主查询。这意味着在融合之前，向量路已经把候选集截断成了 Top-N。

隐患在于：假设有一条记忆，关键词和查询几乎完全匹配（FTS 分数极高），但向量相似度排在 Top-N 之外——它在向量子查询里就被过滤掉了，根本进不了最终融合，于是被漏掉。

正确的做法本该是”先融合、再排序、最后截断”，但受限于单条 SQL 的表达能力，这里用了”先截断、再融合”的近似。数据量越大、Top-N 越小，这个误差越明显。 这是从”单 SQL 方案”换来的隐性代价。

七、什么时候你也该这么选：一个判断清单

讲完代价，给一个可复用的结论。这套方案不是”银弹”，它只在特定边界内是最优解。判断方法很简单，对照下面两个清单：

✅ 该选「SQLite + FTS5 + sqlite-vec」的场景：

  • 单机部署，没有（也不想要）独立检索服务；
  • 向量量级在百万级以下，不需要分布式 ANN；
  • 关键词 + 语义两种检索都要，尤其重视中文关键词命中；
  • 主数据已经在 SQLite 里，想要”检索和业务同库同事务”；
  • 极度重视低运维、易备份——一个文件就是全部状态。

❌ 不该选它的场景：

  • 高并发写入（SQLite 单写者模型是天花板，WAL 只能缓解）；
  • 十亿级向量或需要水平扩展；
  • 需要精细的权限控制、多租户隔离；
  • 团队能承受（且确实需要）Milvus/ES 这类专用服务的运维成本。

一句话概括边界：**”单机 + 中小规模 + 双检索 + 想省心”，选它；一旦规模或并发突破单机上限，就该认真考虑专用向量数据库了。** 判断的锚点永远是第 2 章那六条约束，而不是”哪个技术更火”。

八、总结

这篇文章想说的，其实不是”SQLite 比向量数据库强”，而是一句关于选型的老实话：

技术选型的关键，是”贴合约束”，而不是”技术最强”。

回到开头的问题——“向量检索一定要专门的向量数据库吗？”——答案是：在你的约束允许的范围内，不必。 一个 .sqlite 文件，加上两个原生扩展，就足以支撑单机轻量场景下的记忆与工具检索：FTS5 负责关键词、sqlite-vec 负责语义、触发器负责索引一致性、混合检索负责把它们揉成一个排序。

它不完美——扩展加载脆弱、融合分数是近似、向量预过滤有召回风险——但这些代价，在你”中小规模 + 单机 + 想省心”的前提下，是可以接受、且明码标价的。而真正让它在同类方案里胜出的，是它没有为了”更强”而引入”更重”：没有新服务、没有新存储、没有跨库一致性难题。

下次当你准备为一个万级数据量的检索需求去起一个 Milvus 集群时，不妨先停下来问一句：

这个 .sqlite 文件，是不是已经够了？
